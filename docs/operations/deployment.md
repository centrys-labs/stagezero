# Deployment and recovery boundaries

This page describes the implementation on `origin/main` at `0e3c0ab`, **not** a turnkey production runbook. The repository supplies a PostgreSQL-only local `compose.yaml` and `scripts/install.sh` for server bootstrap; it does not supply a complete API/frontend production deployment manifest. `frontend/svelte.config.js` uses `adapter-auto`; the observed build reports no supported production environment, so select a suitable adapter, hosting target, reverse proxy and HTTPS configuration before calling the frontend deployable. Do not expose the default API listener on `:8080` directly to the public Internet without an intentional ingress/security design.

## Dependencies and sequence

1. Provision PostgreSQL and keep `DATABASE_URL`, a backed-up stable `ENCRYPTION_KEY`, and provider credentials in a secret manager; set `COOKIE_SECURE=true` behind HTTPS and configure OAuth redirect URLs for the chosen public origin. Back up the DB before upgrading. Review [security](security.md).
2. Rehearse all Goose migrations (`api/db/migrate.go`, `api/cmd/migrate/main.go`) on a copy of the existing DB, especially `0018` on rows created before projects/environments. `bun run db:migrate` is deliberately limited to the known local Compose DB; production operators must inspect the target and invoke the raw migration command deliberately. Do not assume `down` restores removed data or remote state.
3. Build and host the Go API and SvelteKit frontend using a **chosen** adapter/ingress plan, with a persistent API process. Configure API routing and server-side `API_BASE_URL` as well as browser `/api` routing; the Vite proxy exists only in development. Startup launches deployment and domain reconcilers inside the API process. Test restart and concurrent requests against the real topology before enabling external access.
4. For managed deployment targets, provision Docker Engine, an SSH account with direct Docker or noninteractive sudo access, firewall access, image-registry access and DNS for requested domains. StageZero installs/manages Traefik remotely; it uses the remote `stagezero` Docker network. Server bootstrap via `scripts/install.sh` is separate from local setup. Verify host-key trust limitations before giving the API privileged credentials.

## Operational behavior

`handlers.CreateDeployment` snapshots configuration (encrypted) into PostgreSQL before starting an in-process `jobs.RunDeploy` goroutine. Deployment logs are persisted and streamed by SSE (`api/broker`); they can be replayed after a browser reconnect. A process crash can interrupt a job; `jobs.StartDeploymentReconciler` attempts startup recovery, but there is no durable external queue or documented multi-instance leader election. Verify the database record **and** remote Docker/Traefik state after an interrupted deployment before retrying. Do not assume a returned HTTP response guarantees remote completion.

With domains the job launches a candidate, checks health, cuts over Traefik and has a route rollback path. Without domains it stops/replaces the running container and downtime is possible. DNS propagation, TLS issuance and remote registry/host connectivity are external dependencies; `jobs.StartDomainReconciler` repairs domain state but cannot replace those services. The local Compose DB is not the remote application host.

## Backups, rollback and visibility

Back up PostgreSQL and `ENCRYPTION_KEY` together; losing the key makes encrypted private keys, environment values and config snapshots unreadable. Preserve SSH key trust records if host verification is added. Restore a DB backup only in a coordinated recovery plan that also inspects remote Docker and Traefik; SQL rollback does not undo containers, images, routes or deleted secrets. There is no configured time-based retention for baseline deployment logs; size/retention and disk usage must be monitored by operators. Check API logs, deployment rows/logs, SSE delivery, proxy readiness and remote container health; the repo does not include a production monitoring stack on `main`. The feature-branch monitoring agent and notifications are documented separately in [metrics](../features/metrics.md).
