# StageZero implementation roadmap

Snapshot: 2026-10-16, default branch `origin/main` (`0e3c0ab`). The two feature branches are **independent proposals**, not shipped capabilities. The [audit](audits/branch-audit.md) gives evidence IDs and precise source locations; [architecture](architecture/overview.md) describes current boundaries. Estimates are rough engineering effort excluding external infrastructure; each item is a separately reviewable change with its own tests. P0 blocks exposure/merge on security or host trust; P1 blocks feature readiness/correctness; P2 makes operation dependable; P3 is optional polish. Do not merge one branch just to enable the other.

## Next five tasks, in order

1. **SZ-01 (P0, GitHub import, ~1–2 days):** protect `POST /api/source/analyze`, bound simultaneous analyses and expanded archive bytes/cancellation, clean temp files. Files: `api/openapi.yaml`, `api/handlers/source.go`, `api/source/source.go`, their tests and generated Go/TS API. **Done:** anonymous abuse fails and a high-expansion/concurrent fixture stays within defined resource budgets; authenticated normal analysis still works. Depends on no feature branch merge; target `feat/github-import`.
2. **SZ-02 (P0, GitHub import, ~1 day):** remove secret `--env KEY=VALUE` process arguments in `api/source/source.go::Prepare` and any equivalent build path. **Done:** fake Railpack/process inspection demonstrates secrets absent from argv and logs while legitimate build env still reaches the build; integration test checks real Railpack behavior. Depends on SZ-01 only for release sequencing; target `feat/github-import`.
3. **SZ-03 (P0, metrics, ~1 day):** redact notification channel configs in `api/handlers/alerts.go`/OpenAPI response and audit remote monitoring-token argument exposure in `api/monitoring/agent.go`. **Done:** ordinary members cannot read delivery URLs/tokens, authorized updates still work, tests assert no sensitive response/process/log output. Independent of GitHub work; target `feat/metrics-mvp`.
4. **SZ-04 (P0, baseline, ~1–2 days):** define host-key enrollment/rotation and replace `InsecureIgnoreHostKey` in `api/ssh/client.go`; update server input/storage/UI as needed, without a trust-on-first-use downgrade hidden from operators. **Done:** unknown/changed server key blocks connection, known key connects, rotation is explicit, all SSH callers and error paths tested. Target default-branch successor before administering production hosts; check both feature branches' changes to `api/ssh/` when integrating.
5. **SZ-05 (P1, metrics, ~1–2 days):** make collection failures/unknown observations distinct from stopped and prevent false starts/resolutions in `monitoring/main.go`, `api/jobs/alerts.go`, `api/alerts/evaluator.go`. **Done:** simulated Docker failure, stale samples and recovery produce correct agent health/incident transitions with repeatable clock-based tests. Target `feat/metrics-mvp`.

## P3: lower-priority decisions

- **SZ-16: retention/capacity policy** (~1 day after SZ-10/14): set explicit baseline deployment-log and agent SQLite retention/backup expectations, test pruning against a disposable DB and long-running deployment history; avoid deleting incident evidence without operator sign-off.
- **SZ-17: advanced repo/monitoring scope** (unestimated, only if requested): decide whether private repositories, webhook deploys, additional providers, or richer alert/channel management have users and an authorization model. Do **not** introduce GitHub App access, an external job queue or a new telemetry backend as part of the MVP fixes without a separate design decision.

For every task: update the relevant docs and tests with the code, run the commands in [testing](development/testing.md), and review the security boundary in [operations/security](operations/security.md). The five-task order front-loads exposed secrets/compute and host trust; GitHub and metrics work can proceed independently. Re-evaluate priorities if the deployment is strictly private or branch SHAs change.
