# SZ-08: GitHub import correctness

## Scope and invariant

Implement G-3 and G-4 on `fix/github-import-correctness`, based on `feat/github-import` after security PRs #5 and #13. The existing image-based project path and the existing add-source-service-to-project path keep working. Only public GitHub repositories are supported. No project or service is deleted as part of this change.

## SZ-08A: Atomic creation and durable retry

Add `POST /api/projects/from-source` with the same owner/developer session requirement as image-based creation. The request contains a client-generated UUID `idempotency_key`, server ID, source URL, explicit branch when the URL identifies a GitHub ref, service name, container name, container port, and optional host port. The response has `project`, `environment`, and `service`, like `CreateProjectFromImageResponse`. Bound request size and validate the key, fields, server ownership, source URL, branch, and ports before writing. The handler uses the existing bounded source analyzer *before* starting a database transaction.

Add a durable PostgreSQL record keyed by `(workspace_id, idempotency_key)` containing a SHA-256 fingerprint of normalized request fields and the JSON response. This table is scoped by the authenticated workspace, not a client-supplied workspace ID. Normalize whitespace/URL and optional fields consistently before hashing; include all fields that affect creation, including the selected branch. A committed record with the same fingerprint returns its saved response with HTTP 201 without re-analyzing or creating anything. Reusing a key with a different fingerprint returns HTTP 409 without touching the original records. A concurrent request with the same key waits for the first transaction, then observes the same saved result or a conflict. A failed transaction leaves neither project, environment, service, source row, nor idempotency record.

Within one transaction, lock the workspace's project-name allocation as the image-based path does; check the idempotency record again; generate a name; create project, production environment, source-backed application service, and its source row; construct a stable response from those rows and the analyzed source; store its serialized JSON in the idempotency record; commit. No GitHub, Railpack, or other network call occurs inside this transaction. Fail before commit if constructing or storing the response fails. Report unique container-name conflicts as 409 and other database failures with non-sensitive errors. The stored response is deliberately a creation-time snapshot; replay must not expose subsequently changed service state or cause side effects. Existing `/api/projects/from-image` and `/api/services/from-source` remain available.

The repository import page replaces the old three-request create sequence with this endpoint. It generates an idempotency key for a submission, retains that key on transport or server error, and retries with the identical payload; it generates a new key only when the user changes the payload. Retain pending key and payload across a page reload in session storage until success or deliberate change, so a lost successful response remains recoverable. On confirmed success, clear pending state and navigate to the returned project. Show distinct, actionable validation, conflict, analysis, and network errors. Never silently create another project on retry.

Existing orphaned projects are not automatically deleted or reused: operators should confirm workspace ownership, inspect environments, services, and deployments, and obtain an explicit decision before any deletion. A pre-existing empty project can be handled through the existing add-service flow rather than guessing that it belongs to this import attempt.

## SZ-08B: Branch URL handling

For a plain `github.com/owner/repo` URL, an omitted branch retains the existing `main` default. A URL containing `/tree/<ref-or-path>` (and a `/blob/<ref-or-path>` link if accepted) is ambiguous whenever its suffix contains slashes: the URL alone cannot distinguish branch name from directory/file path. Both source analysis and source creation must reject such URLs if the branch is omitted or blank rather than discard the URL's ref and silently choose `main`. An explicitly supplied branch must match a whole-segment prefix of the URL suffix; reject a mismatch. The frontend shows the full suffix as an editable suggestion and requires the user to confirm the intended branch before analysis and before submission. A branch with slashes is preserved verbatim after confirmation; no GitHub ref is guessed from a path. Use the existing branch validation and security limits. Include direct API regressions for omitted, mismatched, and confirmed branch, plus frontend interaction/state tests for ambiguous URLs.

## SZ-08C: Source-derived image

For source-backed services, the deployment path continues resolving a fresh commit SHA and deriving `stagezero/<service-id>:<sha>` for the deployment snapshot. The service editor displays source/branch and the most recently deployed derived image or SHA when available, otherwise a clear 'image assigned at deployment' state; it does not offer an editable image input for a source-backed service. Image-based services keep their editable image.

The existing full-resource `PUT /api/services/{id}` remains compatible: for source-backed services the submitted image may equal the currently stored image, but a different value is rejected with HTTP 400/409 and is never persisted. Other valid settings updates remain possible; the image-based path is unchanged. Add a server-side test for a direct API override attempt and for a subsequent source deployment snapshot still deriving the image from its resolved SHA.

## Verification and release boundary

Use deterministic Go tests and disposable PostgreSQL integration tests for rollback on every insert failure, same-key concurrency, different-payload conflict, lost-response replay, authorization/workspace isolation, branch URLs, and source-image overrides. Run API and monitoring Go tests, race tests and vet; frontend check, lint and build; setup tests and generated OpenAPI/sqlc/type drift checks. Browser or live GitHub/Railpack smoke, populated-DB migration rehearsal, and untrusted-build isolation remain independent SZ-09/SZ-11/P0 release gates, not claims of this PR. One focused PR targets `feat/github-import`; no feature-to-main merge, production operation, new dependency, private-repository support, or unrelated refactor.
