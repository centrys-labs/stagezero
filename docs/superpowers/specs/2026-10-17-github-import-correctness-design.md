# SZ-08: GitHub import correctness

## Scope and invariant

Implement G-3 and G-4 on `fix/github-import-correctness`, based on `feat/github-import` after security PRs #5 and #13. The existing image-based project path and the existing add-source-service-to-project path keep working. Only public GitHub repositories are supported. No project or service is deleted as part of this change.

## SZ-08A: Atomic creation and durable retry

Add `POST /api/projects/from-source` with the same owner/developer session requirement as image-based creation. The request contains a client-generated UUID `idempotency_key`, server ID, original source URL, explicit branch and confirmation for a URL identifying a GitHub ref, service name, container name, container port, and optional host port. The response has `project`, `environment`, and `service`, like `CreateProjectFromImageResponse`. Authenticate and authorize every request, including replay; bound the body and validate the key, fields, server ownership, original URL, branch confirmation, and ports before reading idempotency state or invoking the analyzer.

Add a durable PostgreSQL record keyed by `(workspace_id, idempotency_key)` containing a SHA-256 fingerprint of normalized request fields and the JSON response. The workspace comes from the authenticated session, never the payload. Canonicalize URL/whitespace and optional fields consistently, but preserve the original URL until ref validation finishes and preserve the branch's exact case in the fingerprint: `Feature/X` and `feature/x` are different requests. Include every creation-affecting field, including server, port, ref suffix, and explicit branch. After validation/normalization, calculate the fingerprint and look up an existing committed result **before any GitHub/Railpack analysis**: matching fingerprint returns its saved response with HTTP 201; different fingerprint returns HTTP 409. An authorized same-key retry after a successful commit never repeats source analysis. Retain committed keys and responses for the lifetime of their workspace (no time-based expiry or silent pruning); replay returns the creation-time snapshot, not a current project/service read. Workspace deletion cascades the idempotency rows. A concurrent same-key request can analyze while the first is still in flight, but must wait on the creation transaction and return the first committed result or conflict; a failed transaction leaves neither project, environment, service, source row, nor idempotency record.

For a new key only, reuse the *same* authenticated source-analysis gate and limits as `/api/source/analyze`: per-user rate and per-process concurrency controls, request-size and read deadlines, 90-second analysis deadline, bounded tarball/extraction/output/entries, cancellation and temp-tree/process-group cleanup, and the existing safe GitHub fetch/redirect checks. Do not create a second, unmetered analyzer path; release the gate on every exit. This shared gate's existing single-API-replica/shared-ingress assumption remains an operational release constraint. Complete network analysis *before* starting a database transaction.

Within one transaction, lock the workspace's project-name allocation as the image-based path does; recheck the idempotency record under that lock; generate a name; create project, production environment, source-backed application service, and its source row; build the **complete** creation response from transaction-visible returned rows and analyzed source; serialize and store those exact response bytes in the idempotency record; commit. Do not use `serviceResponse` or any other helper that queries uncommitted rows through a separate pooled connection. Concurrent transactions for the same workspace serialize before the second idempotency check; only the first committed transaction creates records. No GitHub, Railpack, or other network call occurs inside this transaction. Fail before commit if constructing or storing the response fails. Report unique container-name conflicts as 409 and other database failures with non-sensitive errors. Replay must not cause side effects. Existing `/api/projects/from-image` and `/api/services/from-source` remain available.

The repository import page replaces the old three-request create sequence with this endpoint. It generates an idempotency key for a submission, retains that key on transport or server error, and retries with the identical payload; it generates a new key only when the user changes the payload. Retain pending key and payload across a page reload in session storage until success or deliberate change, so a lost successful response remains recoverable. On confirmed success, clear pending state and navigate to the returned project. Show distinct, actionable validation, conflict, analysis, and network errors. Never silently create another project on retry.

Existing orphaned projects are not automatically deleted or reused: operators should confirm workspace ownership, inspect environments, services, and deployments, and obtain an explicit decision before any deletion. A pre-existing empty project can be handled through the existing add-service flow rather than guessing that it belongs to this import attempt.

## SZ-08B: Branch URL handling

For a plain `github.com/owner/repo` URL, an omitted branch retains the existing `main` default. A URL containing `/tree/<ref-or-path>` or a supported `/blob/<ref-or-path>` link is ambiguous: even a suffix of `main` must not be inferred from a defaulted form value, and a suffix with slashes cannot distinguish branch name from directory/file path. A shared validation path must inspect the **original** URL before reducing it to owner/repo. For these URLs, `/api/source/analyze`, the new atomic endpoint, and the existing `/api/services/from-source` all require a nonblank, explicitly supplied branch **and** `branch_confirmed: true`; otherwise return 400 without analysis or a write. The branch must match a case-sensitive, whole-segment prefix of the URL suffix; reject a mismatch. The frontend resets confirmation whenever the URL or branch changes, displays the complete suffix as an editable suggestion, and sets `branch_confirmed` only after an explicit user confirmation at analysis and submission. A defaulted `main` never sets that flag. A branch with slashes is preserved verbatim after confirmation; no GitHub ref is guessed from a path. Use the existing branch validation and security limits. Include direct API regressions for omitted/defaulted/unconfirmed, mismatched, and confirmed branch, plus frontend interaction/state tests for ambiguous URLs.

## SZ-08C: Source-derived image

For source-backed services, the deployment path continues resolving a fresh commit SHA and deriving `stagezero/<service-id>:<sha>` for the deployment snapshot. The service editor displays source/branch and the most recently deployed derived image or SHA when available, otherwise a clear 'image assigned at deployment' state; it does not offer an editable image input for a source-backed service. Image-based services keep their editable image.

The existing full-resource `PUT /api/services/{id}` remains compatible: for source-backed services the submitted image may equal the currently stored image, but a different value is rejected with HTTP 400/409 and is never persisted. Other valid settings updates remain possible; the image-based path is unchanged. Add a server-side test for a direct API override attempt and for a subsequent source deployment snapshot still deriving the image from its resolved SHA.

## Verification and release boundary

Use deterministic Go tests and disposable PostgreSQL integration tests for rollback on failed inserts or response serialization, simultaneous same-key requests, same key/different payload or branch case, lost-response replay with **no second analysis call**, authorization on replay and workspace isolation, shared rate/concurrency/deadline/body limits on creation, original-URL branch confirmation in all three endpoints, and source-image overrides. Run API and monitoring Go tests, race tests and vet; frontend check, lint and build; setup tests and generated OpenAPI/sqlc/type drift checks. Browser or live GitHub/Railpack smoke, populated-DB migration rehearsal, and untrusted-build isolation remain independent SZ-09/SZ-11/P0 release gates, not claims of this PR. One focused PR targets `feat/github-import`; no feature-to-main merge, production operation, new dependency, private-repository support, or unrelated refactor.
