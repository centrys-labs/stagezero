# SZ-11B: combined migration integrity gate

## Scope and release boundary

Integrate the current `feat/github-import` and `feat/metrics-mvp` tips in a new `integration/sz11b-candidate` branch, resolving their six known code conflicts without dropping either feature's behavior or security fixes. Keep the source and Metrics feature branches and `main` unchanged. Open a focused `fix/sz11b-migration-integrity` PR against the candidate, not `main`. The integrity gate belongs only to the combined candidate; a standalone feature checkout is not expected to contain the other feature's migrations.

The combined SQL migration history is exactly versions 0001–0031. Source owns `0026_service_sources.sql` and `0031_source_project_idempotency.sql`; Metrics owns `0027_server_monitoring.sql`, `0028_alerts.sql`, `0029_drop_monitoring_private_address.sql`, and `0030_monitoring_pending.sql`. Existing SQL migration contents and applied histories are not rewritten. No production database, live host, untrusted build, or feature-branch-to-`main` merge is in scope.

## Gate contract

Ship a versioned, embedded manifest in `api/db/migrations/manifest-0031.json` listing each of the 31 expected SQL filenames with its SHA-256 digest. Pin the manifest's own SHA-256 digest in Go source so accidentally editing both an SQL file and its manifest does not silently redefine the accepted bundle. The manifest is a release inventory, not an adversarial signature: a code author who changes both the manifest and the pinned digest can intentionally publish a new bundle. Updating it for future migrations requires an explicit review of the new version and SQL content.

Before `goose.Up`, check the embedded migration directory against that inventory: every expected filename exists exactly once, its file bytes match the digest, the manifest bytes match the pinned digest, and no unexpected `.sql` file, duplicate version, or version beyond 0031 exists. An invalid bundle returns an actionable error without invoking Goose or modifying the database. Use the same embedded filesystem passed to Goose; do not trust a separate working-directory copy.

After a successful `goose.Up(..., goose.WithAllowMissing())`, query `goose_db_version` rather than relying on Goose's reported current-version pointer. For each version, use its latest row by `id` to determine the effective `is_applied` state. Require exactly versions 1–31 active, with no unknown nonzero version or unapplied expected version; ignore Goose's version-zero bootstrap row. Reject missing history or an inaccessible database. Validate the critical combined schema against PostgreSQL catalogs: the source tables and their workspace/service foreign keys and idempotency primary key; Metrics monitoring columns, their retention check, unique monitoring FQDN indexes, alert tables, their workspace/scope foreign keys and scope check, and the active-alert unique index. Also assert that the removed `monitoring_private_address` column is absent. Report precise failures, never silently repair or mark rows applied. A structural check guards against a migration row being present while the expected schema is absent; it does not prove every database object or historical data value is pristine. A postflight failure is an error requiring manual investigation, not an automatic rollback of migrations already committed by Goose.

Run the checks from the combined candidate's migration entry point (`api/db.RunMigrations`) so CLI and startup callers cannot skip them. Keep normal `goose.Down` behavior unchanged in this focused PR, but document that it is **not** a safe release rollback: with out-of-order application it can remove an unexpected lower version, and rolling back 0031 destroys durable idempotency responses. Restore a verified backup into a disposable environment, validate data and migration history, then plan a forward repair instead of running ordinary Down on a populated release database.

## Integration and verification

First merge the two feature tips into the candidate with an explicit resolution record for `api/config/config.go`, `api/gen/api.gen.go`, `api/jobs/deploy.go`, `api/main.go`, `api/ssh/shell.go`, and `frontend/src/routes/(app)/(builder)/+layout.svelte`. Review semantic auto-merges too, regenerate Go/TypeScript API and sqlc outputs, and run backend/frontend tests before using the candidate as the PR base. Do not resolve a conflict by simply choosing one branch's entire implementation if it discards the other feature.

Use disposable PostgreSQL 18 databases to exercise four paths: fresh combined install; populated `main` (v25) to combined; populated Metrics-first (v30, missing 0026) to combined; and populated source-first (v31, missing 0027–0030) to combined. Seed representative users, workspaces, server and service mappings; retain source/idempotency data on the source path and alert/monitoring data on the Metrics path. Check the exact effective applied set, data counts, key foreign keys, unique and check constraints, and a second `RunMigrations` that makes no changes. An out-of-order path may leave Goose's reported current version below 31; this must not be mistaken for a missing effective migration.

Negative tests must exercise the same validation seam as the real embedded bundle: remove `0028_alerts.sql` from a test filesystem and assert preflight fails before Goose and before any database changes; mutate an SQL file and the manifest bytes independently and assert each fails closed; simulate a missing/unapplied effective version and a dropped critical index or constraint after migration and assert the postflight fails. Verify a valid bundle and schema pass. Run `go test ./...`, `go test -race ./...`, `go vet ./...`, `go build ./...`, frontend check/lint/build, setup tests, generated-code drift checks, and `git diff --check` on the combined candidate/PR head; report any infrastructure-dependent skips honestly. Do not make the test runner require a real persistent database by default: gate disposable-PostgreSQL tests behind an explicit test URL.

The focused PR must describe its candidate base, conflict-resolution evidence, fail-closed tests, remaining limitations, and whether the combined branch is ready for the separately authorized SZ-09 live smoke. This work neither executes SZ-09 nor grants permission to expose untrusted Railpack execution on an API host.
